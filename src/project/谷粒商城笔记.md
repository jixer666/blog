## Nginx 搭建

访问链路：Nginx -> 网关 -> 具体服务

### Host 配置

打开文件 `‪C:\Windows\System32\drivers\etc\hosts`，添加下行文字，保存并覆盖（需要用管理员权限）

```
127.0.0.1 gulimall.com
```

原理：浏览器在访问 `gulimall.com` 这个网站的时候，会先从本机中的 Host 文件去查找是否存在，否存在就返回对应设置的 IP 地址；若不存在就去解析  `gulimall.com` 去获取真实的 IP 地址

### Nginx 配置

作用：方向代理 + 负载均衡

注意：必须要添加 `proxy_set_header Host $host` ，否则在 `Nginx`  反向代理到网关是没有 `Host` 这个参数的，网关就匹配不到出现404错误

```nginx
http {
    include       mime.types;
    default_type  application/octet-stream;
    sendfile        on;
    keepalive_timeout  65;

    upstream gulimall {
        server 127.0.0.1:88;
    }

    server {
        listen       80;
        server_name  gulimall.com;

        location / {
            proxy_pass http://gulimall;
            proxy_set_header Host $host;
        }

        error_page   500 502 503 504  /50x.html;
        location = /50x.html {
            root   html;
        }
    }

}

```

### 压力测试

**常用的性能指标**

- HPS：每秒点击次数

- TPS：系统每秒处理交易数

- QPS：系统每秒处理查询次数

  对于互联网业务中，如果某些业务有且仅有一个请求连接，那么TPS = QPS = HPS，一 般情况下用 TPS 来衡量整个业务流程，用 QPS 来衡量接口查询次数，用 HPS 来表 示对服务器单击请求

- 吞吐量：每秒钟系统能够处理的请求数、任务数

- 响应时间：服务处理一个请求或一个任务的耗时

- 错误率：一批请求中结果出错的请求所占比例

### Redission分布式锁入门

#### 看门狗机制

作用：对使用 `lock` 方法的锁进行自动续期

Redission 的 `lock` 方法源代码中，若是没有传入值，就会创建一个定时任务，定时任务的默认时间是10s（看门狗的有效时间是30s，30 / 3 = 10），每10s会更新有效期。具体代码如下：

```java
private void renewExpiration() {
    ExpirationEntry ee = (ExpirationEntry)EXPIRATION_RENEWAL_MAP.get(this.getEntryName());
    if (ee != null) {
        Timeout task = this.commandExecutor.getConnectionManager().newTimeout(new TimerTask() {
            public void run(Timeout timeout) throws Exception {
                ExpirationEntry ent = (ExpirationEntry)RedissonLock.EXPIRATION_RENEWAL_MAP.get(RedissonLock.this.getEntryName());
                if (ent != null) {
                    Long threadId = ent.getFirstThreadId();
                    if (threadId != null) {
                        RFuture<Boolean> future = RedissonLock.this.renewExpirationAsync(threadId); // 设置有效期
                        future.onComplete((res, e) -> {
                            if (e != null) {
                                RedissonLock.log.error("Can't update lock " + RedissonLock.this.getName() + " expiration", e);
                            } else {
                                if (res) {
                                    RedissonLock.this.renewExpiration();
                                }
                            }
                        });
                    }
                }
            }
        }, this.internalLockLeaseTime / 3L, TimeUnit.MILLISECONDS); // internalLockLeaseTime默认是30s
        ee.setTimeout(task);
    }
}
```

### 缓存一致性

#### 双写模式

在修改完数据库后，立刻取修改缓存，能够保证强一致性

缺点：高并发下容易出现脏数据，如下如所示：

![https://gitee.com/lijunxi666/picture-bed/raw/master/gulimall/Snipaste_2025-08-12_19-47-57.png](https://gitee.com/lijunxi666/picture-bed/raw/master/gulimall/Snipaste_2025-08-12_19-47-57.png)

#### 失效模式

- 方案一：修改完数据库后，删除缓存

  缺点：高并发下容易出现脏数据，如下图所示：

  ![https://gitee.com/lijunxi666/picture-bed/raw/master/gulimall/Snipaste_2025-08-12_19-52-44.png](https://gitee.com/lijunxi666/picture-bed/raw/master/gulimall/Snipaste_2025-08-12_19-52-44.png)

- 方案二：删除完缓存后，修改数据库

  缺点：容易出现脏数据

  线程 A 删完缓存后，线程 B 来查询缓存，此时不存在，就去查询数据库，加入缓存。然后线程 A 才更数据库，缓存中已存放了更新之前的值

**方案一解决方案**：

Cancal 订阅 MySQL binlog 日志

原理：数据库表更新字段信息后会写入 binlog 日志，用 Cancal 去监听 binlog，发送 MQ 来删除对应数据缓存

**方案二解决方案**

延时双删

再删除完缓存，修改完数据库后，延时一段时间（时间大于读数据 + 写缓存，一般为3~5秒），再去删除缓存。在删除缓存但未修改数据库期间，其他线程查询数据库向缓存中加入了旧数据，N 秒后会再次被删除

### SpringCache

#### 四种注解

SpringCache 有四种注解如下：

- @Cacheable：缓存方法返回的数据，key 这里设置的是方法名（也可以设置为方法的某一个参数，更具有灵活性），value 用于分组

  用法：`@Cacheable(value = "categoryCache", key="#root.method.name")`

- @CachePut：更新缓存为方法返回的数据

  用法：`@CachePut(value = "categoryCache", key="'getCache'")`

- @CacheEvict：删除缓存

  用法：`@CacheEvict(value = "categoryCache", key="'getCategoryListWithSpringCache'")`

- @Caching：组合操作

  用法：进行多个缓存删除

  ```java
  @Caching(evict = {
          @CacheEvict(value = "categoryCache", key = "'getCategoryListWithSpringCache'"),
          @CacheEvict(value = "categoryCache", key = "'getCache'")
  })
  // 上面的多次删除的注解等同于下面，删除同一种 value 的所有缓存
  @CacheEvict(value = "categoryCache", allEntries = true)
  ```

#### 自定义缓存配置

这里以 Redis 缓存为例，参考 `autoconfigure/cache/RedisCacheConfiguration` 的 `determineConfiguration` 方法的配置，自定义缓存的过期时间、缓存前缀和缓存序列化方式等

```java
@EnableCaching
@Configuration
@EnableConfigurationProperties(CacheProperties.class)
public class MyCacheConfig {
    @Bean
    public RedisCacheConfiguration redisCacheConfiguration(CacheProperties cacheProperties) {
        RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig();
        config.serializeKeysWith(RedisSerializationContext.SerializationPair.fromSerializer(new StringRedisSerializer()));
        config.serializeValuesWith(RedisSerializationContext.SerializationPair.fromSerializer(new GenericJackson2JsonRedisSerializer()));
        CacheProperties.Redis redisProperties = cacheProperties.getRedis();
        if (redisProperties.getTimeToLive() != null) {
            config = config.entryTtl(redisProperties.getTimeToLive());
        }
        if (redisProperties.getKeyPrefix() != null) {
            config = config.prefixKeysWith(redisProperties.getKeyPrefix());
        }
        if (!redisProperties.isCacheNullValues()) {
            config = config.disableCachingNullValues();
        }
        if (!redisProperties.isUseKeyPrefix()) {
            config = config.disableKeyPrefix();
        }
        return config;
    }
}
```

#### 总结

SpringCache 适用于读多写少、一致性要求不高的场景

对于缓存三剑客问题：

- 缓存穿透：加配置 `spring.cache.redis.cache-null-values=true`解决

- 缓存击穿：单机模式上注解加 `@Cacheable(value = "categoryCache", key="#root.method.name", sync = true)` 可以解决，本质上使用 synchronized 来锁住获取方法，源码如下，但分布式下无法解决

  ```java
  public synchronized <T> T get(Object key, Callable<T> valueLoader) {
      Cache.ValueWrapper result = this.get(key);
      if (result != null) {
          return result.get();
      } else {
          T value = valueFromLoader(key, valueLoader);
          this.put(key, value);
          return value;
      }
  }
  ```

- 缓存雪崩问题：加随机的过期时间，还需要特殊化定制

### CompletableFuture 异步编排

1、无返回值

```java
CompletableFuture.runAsync(() -> {
    System.out.println("无返回结果");
});
```

2、有返回值

```java
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
    System.out.println("有返回结果");

});
```

3、完成时回调

```java
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
    System.out.println("有返回结果");
    return 10 / 2;
}).whenComplete((result, exception) -> {
    try {
        Thread.sleep(2000);
        System.out.println("休眠结束");
    } catch (InterruptedException e) {
        throw new RuntimeException(e);
    }
});

// 异步处理
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
    System.out.println("有返回结果");
    return 10 / 2;
}).whenCompleteAsync((result, exception) -> {
    try {
        Thread.sleep(2000);
        System.out.println("休眠结束");
    } catch (InterruptedException e) {
        throw new RuntimeException(e);
    }
});
```

4、数据转换（类似于 stream 流的 map）

```java
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> 10 / 2)
    .thenApply(result -> {
        System.out.println("转换前: " + result); 
        return "结果是: " + result;
    });
```

5、 合并两个结果

```java
CompletableFuture<Integer> future1 = CompletableFuture.supplyAsync(() -> 10);
CompletableFuture<Integer> future2 = CompletableFuture.supplyAsync(() -> 20);

CompletableFuture<Integer> combined = future1.thenCombine(future2, (result1, result2) -> {
    System.out.println("结果1: " + result1);  // 输出: 结果1: 10
    System.out.println("结果2: " + result2);  // 输出: 结果2: 20
    return result1 + result2;
});

System.out.println(combined.get());  // 输出: 30
```

6、处理异常

```java
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
    System.out.println("有返回结果");
    return 10 / 2;
}).exceptionally(throwable -> {

```

```java
CompletableFuture<Integer> future = CompletableFuture.supplyAsync(() -> {
    System.out.println("有返回结果");

}).handle((res, error) -> {

});
```

8、A、B 两个线程，A 执行完后在执行 B

10、A、B 两个线程，在两个线程只要其中一个执行完后执行 C

```java
CompletableFuture<Integer> f1 = CompletableFuture.supplyAsync(() -> {
    System.out.println("任务一");
    return 1;
});

    try {
        Thread.sleep(1000);
        System.out.println("任务二");
    } catch (InterruptedException e) {
        throw new RuntimeException(e);
    }
    return 2;
});

// 无需返回值
f1.runAfterEither(f2, () -> {
    System.out.println("任务一或者任二其中一个处理完成");
});

// 有返回值

    System.out.println("任务一或者任二其中一个处理完成，处理结果：" + res); // res输出1

// 处理为新结果
CompletableFuture<String> future = f1.applyToEither(f2, (res) -> {
    System.out.println("任务一或者任二其中一个处理完成，处理结果：" + res); // res输出1
    return "新结果" + res; // 输出 新结果1
});
```

```java
// 三个任务都执行完
CompletableFuture.allOf(f1, f2, f3).get();
// 三个任务其中一个执行完
CompletableFuture.anyOf(f1, f2, f3).get();
System.out.println("所有任务都执行完成");
```

## Session 共享问题

登录成功后，将用户信息存在 session 中，但是因为 session 本质上是一个本地的 map，存在以下问题：

- 相同服务，不同实例之间无法共享
- 不同服务之前无法共享

登陆后需要将 `JESSSION` 信息返回给浏览器，浏览器存放在 cookie，下一次带着 cookie 就能够知道用户的身份

相同服务，不同实例之间无法共享，有以下方法：

### 不同实例无法共享解决办法

#### Session 复制

原理：多个 tomcat 之间采用同步方法来保证每个 tomcat 的 session 一致	

优点：tomcat 原生支持，操作简单只需要修改配置文件

缺点：

- 同步需要占用网络带宽，会降低业务的处理能力
- 若一个台 tomcat session 内存有 1g，那么 100 台内存需要 100g。可以水平拓展，但受到内存限制

#### 客服端存储

原理：将保存用户信息的 session 存在 cookie 中返回前端

优点：简单

缺点：

- 不安全，存在用户信息篡改等问题
- 若用户信息很多，传输需要占用网络带宽，并且受到 cookie 最大长度限制，最多只能 4k

不采用此方法

#### hash 一致性

原理：每个用户 IP 或者业务字段 ID 计算 hash 值，然后模当前的实例数量，算出从哪一个实例中获取用户下信息	

优点：

- 简单只需要修改 nginx 配置
- 支持水平拓展

#### Redis 统一存储

原理：将序列化的 session 信息保存在 Redis 中

优点：

- 重启无需担心数据丢失
- 支持水平拓展

缺点：查询数据增加一次网络调用

**本次采用此方法**

添加 SpringSession 依赖，无需改动之前的对 session 操作代码，具体见 `gulimall-auth` 模块下的 `OAuth2Controller` 类

将 JDK 序列化器更换为 Json 序列化配置

```java
@Bean
public RedisSerializer<Object> springSessionDefaultRedisSerializer() {
    return new GenericJackson2JsonRedisSerializer();
}
```

**Redis 自动续期**

页面上每一次操作都会自动刷新 Redis 中 session 的有效期

### 不同服务无法共享解决办法

将 cookie 作用域设置为父域名：gulimall.com 即可

```java
@Bean
public CookieSerializer cookieSerializer() {
    DefaultCookieSerializer defaultCookieSerializer = new DefaultCookieSerializer();
    // 使用父域名，解决不同服务session不共享的问题
    defaultCookieSerializer.setDomainName("gulimall.com");
    defaultCookieSerializer.setCookieName("GULIMALLSESSION");
    return defaultCookieSerializer;
}
```

### SpringSession 原理

使用拦截器，将原有的 HttpSession 替换为包装的对 Redis 操作的 Session 对象，代码如下：

`SessionRepositoryFilter` 类

```java
protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain) throws ServletException, IOException {
    request.setAttribute(SESSION_REPOSITORY_ATTR, this.sessionRepository);
    SessionRepositoryFilter<S>.SessionRepositoryRequestWrapper wrappedRequest = new SessionRepositoryRequestWrapper(request, response, this.servletContext);
    SessionRepositoryFilter<S>.SessionRepositoryResponseWrapper wrappedResponse = new SessionRepositoryResponseWrapper(wrappedRequest, response);
    try {
        // 传递的是包装后的类
        filterChain.doFilter(wrappedRequest, wrappedResponse);
    } finally {
        wrappedRequest.commitSession();
    }
}
```

这里使用到了装饰器设计模式

我们在获取 session 的时候，通过在方法参数中写入 `HttpSession session` 或者 `HttpServletRequest request` 的 `request.getSession()` ，这里获取到的就是已经包装后的 session，操作全是对 redis 进行的

### 消息堆积、丢失和重复

这部分应用场景是提交订单的时候用了延时队列，可能会出现以上的几种情况，解决办法见如下

**1、消息丢失**

- 生产者发送消息因网络原因导致发送失败，可以加一个消息发送记录表来存放消息记录，做个定时任务扫描未发送成功状态的数据进行重试

- 消息到达 Broker，但在存放到队列中失败，可以在后端开启确认回调机制，对回调失败的进行重试，具体代码见 `gulimall-order` 模块的 config 文件夹下的 `GulimallMQConfig`

  ```java
  rabbitTemplate.setConfirmCallback()
  ```

- 消息消费的时候出错，可以开启手动 ACK 机制

**2、消息重复**

- 添加消息处理记录表，对每一条处理成功的消息的 ID 的进行记录
- 查询的时候做幂等性处理，例如只查询出未处理的订单

**3、消息堆积**

- 消费者消费能力不行、生产者宕机或者某一瞬间发送的消息过多导致，可以添加消费者数量
- 还可以把队列的消息全部取出来存放数据库，让 MQ 能够正常消费数据，然后专门做一个服务处理存放在数据库的消息

订单模块（带有登录信息）远程调用购物车模块（无登录信息），没有带上登录信息，排查原因发现请求头中并未带上订单模块的 cookie 信息，源码分析如下：

SynchronousMethodHandler 类

```java
 Object executeAndDecode(RequestTemplate template) throws Throwable {
   Request request = targetRequest(template);
   if (logLevel != Logger.Level.NONE) {
     logger.logRequest(metadata.configKey(), logLevel, request);
   }
   Response response;
   long start = System.nanoTime();
   try {
     // 执行调用
     response = client.execute(request, options);
   } catch (IOException e) {
     if (logLevel != Logger.Level.NONE) {
       logger.logIOException(metadata.configKey(), logLevel, e, elapsedTime(start));
     }
     throw errorExecuting(request, e);
   }
   // 省略
 }
```

断点看出远程调用请求会封装成一个 RequestTemplate 对象，包含了请求路径、请求头等信息，template 是一个请求对象，有请求路径，但无请求头 cookie，所以请求过去就无用户信息

```java 
@Configuration
public class GulimallFeignConfig {
    @Bean("requestInterceptor")
    public RequestInterceptor requestInterceptor() {
        return new RequestInterceptor() {
            @Override
            public void apply(RequestTemplate template) {
                // 拿到当前线程的请求头，本质上是一个ThreadLocal
                ServletRequestAttributes requestAttributes = (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
                String cookie = requestAttributes.getRequest().getHeader("Cookie");
                // 放入cookie到template请求中
                template.header("Cookie", cookie);
            }
        };
    }
}
```

### 本地事务

注意以下几点：

- 事务异常传播
- 都需要走代理对象

案例一：生效

```java
@Override
@Transactional(rollbackFor = Exception.class)  // 事务A开始
public void save() {
    orderDao.saveTest(new Test(2, "222"));  // 在事务A中
    test1();  // 自调用，test1的@Transactional不生效，仍在事务A中
    orderDao.saveTest(new Test(3, "333"));  // 在事务A中（但不会执行到）
}

@Transactional(rollbackFor = Exception.class)  // 这个注解被忽略！
public void test1() {
    orderDao.saveTest(new Test(1, "111"));  // 在事务A中
    int a = 1 / 0;  // 异常抛出到save()方法
}
// 事务A回滚 - 所有操作(id=2, id=1)都回滚
```

案例二：生效

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void save() {
    orderDao.saveTest(new Test(2, "222"));
    test1();
    orderDao.saveTest(new Test(3, "333"));
}

public void test1() { // 无论是 private 还是 public 都生效
    orderDao.saveTest(new Test(1, "111"));
    int a = 1 / 0;
}
```

### 分布式事务

不同服务之间，因某一个或多个服务出现问题（网络等原因），需要这链路上的所有服务都要进行回滚，要么全部成功，要么全部失败

分布式事务分为两种：

- 刚性事务：遵循 ACID 原则，强一致性

- 柔性事务：遵循 BASE 理论，最终一致性

分布式事务实现四种方案如下

#### 2PC 模式（刚性事务）

2PC 又叫 XA Transactions，是一个两阶段提交协议

![https://gitee.com/lijunxi666/picture-bed/raw/master/gulimall/Snipaste_2025-11-16_13-38-38.png](https://gitee.com/lijunxi666/picture-bed/raw/master/gulimall/Snipaste_2025-11-16_13-38-38.png)

第一阶段：事务协调器要求每个涉及到事务的数据库预提交此操作，并反映是 否可以提交

第二阶段：事务协调器要求每个数据库提交数据

其中，如果有任何一个数据库否决此次提交，那么所有数据库都会被要求回滚它们在此事务 中的那部分信息

优点：

- XA 协议实现简单，一旦商业数据库实现了 XA 协议，使用分布式事务的成本也比较低。

缺点：

- **性能不理想**，特别是在交易下单链路，往往并发量很高，XA 无法满足高并发场景
- 目前在商业数据库支持的比较理想，在 MySQL 数据库中支持的不太理想（MySQL 的 XA 实现，没有记录预提交阶段日志，主备切换回导致主库与备库数据不一致）

3PC 模式是将 2PC 模式的第一阶段分成了两个阶段：先是询问是否能够提交，然后才是准备数据预提交

#### TCC 事务补偿型方案（柔性事务）

TCC 模式：把自定义的分支事务纳入到全局事务管理中

![https://gitee.com/lijunxi666/picture-bed/raw/master/gulimall/Snipaste_2025-11-16_13-52-19.png](https://gitee.com/lijunxi666/picture-bed/raw/master/gulimall/Snipaste_2025-11-16_13-52-19.png)

一阶段 prepare 行为：调用自定义的 prepare 逻辑

二阶段 commit 行为：调用自定义的 commit 逻辑

三阶段 rollback 行为：调用自定义的 rollback 逻辑

> 说白了 TCC 事务补偿就是 3PC 的手动版

#### 最大努力通知型方案（柔性事务）

对服务进行通知，但不一定能够保证通知成功，但会提供可查询操作接口进行核对

例如支付宝支付成功回调接口就是一种最大努力通知型

#### 可靠消息 + 最终一致性方案（异步确保型）

服务在发生错误的时候回向 MQ 发送消息，然后服务就从 MQ 中收到这些消息，进行回滚

### CAP 定理

- **一致性**（Consistency）

  分布式事务一致性的三个概念：

  - 强一致性：必须保证任何时刻都是一致的
  - 弱一致性：允许出现部分不一致
  - 最终一致性：数据在一段时间后，最终保证一致

- **可用性**（Availability）

- **分区容错性**（Partition tolerance）：大多数分布式系统都分布在多个子网络。每个子网络就叫做一个区（partition）。 分区容错的意思是，区间通信可能失败。比如，一台服务器放在中国，另一台服务 器放在美国，这就是两个区，它们之间可能无法通信。

分布式系统一般组合是 CP 或 AP，分区容错性是必须要要有的，一致性和可用性无法同时拥有，所以也就是**无法三者兼顾**

### BASE 理论

BASE 理论是对 CAP 定理的延伸，思想是无法做到强一致性，就允许弱一致性，但最终要达到**最终一致性**

BASE 是指：

- **基本可用**（BasicallyAvailable）：允许出现损失部分功能可用性（响应时间、功能等），但要保证总体可用

  例如：购物网站在双十一时，为了保护系统的稳定性， 部分消费者可能会被引导到一个降级页面

- **软状态**（ SoftState）：允许系统存在中间状态，而该中间状态不会影响系统整体可用性。分布式存储中一般一份数据会有多个副本，允许不同副本同步的延时就是软状态的体 现

  例如：一个状态有成功和失败两种状态，现在加一个中间状态正在进行中，这就是软状态

- **最终一致性**（ EventualConsistency）：系统中的数据经过一段时间后数据是一致的

## 延时队列

```java
@Configuration
public class GulimallSentinelConfig {
    /**
     * 自定义错误响应
     */
    public GulimallSentinelConfig() {
        WebCallbackManager.setUrlBlockHandler(new UrlBlockHandler() {
            @Override
            public void blocked(HttpServletRequest httpServletRequest, HttpServletResponse httpServletResponse, BlockException e) throws IOException {
                R result = R.error(e.getMessage());
                httpServletResponse.setContentType("application/json;charset=UTF-8");
                httpServletResponse.getWriter().write(JSON.toJSONString(result));
            }
        });
    }
}
```
